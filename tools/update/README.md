# Оновлення VRX-GL з USB-флешки

Станція на кожному завантаженні перевіряє всі USB-флешки. Якщо знаходить
каталог `VRX-update` з версією, відмінною від встановленої, — оновлюється
й показує лог на екрані. Якщо версія та сама або каталогу немає —
завантажується мовчки, під заставкою, ніби нічого не сталось.

## Структура на флешці

Каталог `VRX-update` кладеться **в корінь флешки**:

```
<флешка>/
└── VRX-update/
    ├── version.txt        версія цієї збірки
    ├── update_list        список файлів із підписами
    ├── osd_config.json    ← файли за тими самими шляхами,
    └── build/                що й у корені станції
        └── vrx_gl
```

## Як рахуються шляхи

Корінь станції — `/root/vrx-gl`. Усі шляхи в `update_list` рахуються
**від нього**, і точно так само від каталогу `VRX-update` на флешці.

| у списку | звідки береться | куди лягає |
|---|---|---|
| `osd_config.json` | `VRX-update/osd_config.json` | `/root/vrx-gl/osd_config.json` |
| `build/vrx_gl` | `VRX-update/build/vrx_gl` | `/root/vrx-gl/build/vrx_gl` |
| `img/horizont_0.png` | `VRX-update/img/horizont_0.png` | `/root/vrx-gl/img/horizont_0.png` |

Тобто каталог `VRX-update` — це дзеркало кореня станції, у якому лежить
лише те, що змінилось.

Заборонено: абсолютні шляхи (`/etc/passwd`), вихід угору (`../`),
самопосилання (`./`) і подвійні слеші. Такий рядок зупиняє все
оновлення цілком.

## version.txt

Один рядок, будь-який текст. Прийнято дату збірки:

```
20260815
```

Порівнюється **на рівність, а не на «більше»**. Якщо версія на флешці
відрізняється від встановленої — оновлення піде, навіть якщо номер
менший. Це зроблено навмисно: так можна відкотити невдалу збірку в полі,
просто підклавши флешку зі старою версією.

## update_list

По рядку на файл: підпис, два пробіли, шлях.

```
# коментарі та порожні рядки ігноруються
d31a1ce3a572957a75bcd4dd4a0aede949e97983324c86462571fe2245557bda  build/vrx_gl
79d51585432fcff298ac25bcd2e4bc65fde7e37915f2647aba0d37662e8fc30d  osd_config.json
```

Підпис — **HMAC-SHA256** від вмісту файла з секретним ключем станції.
Не просто «хеш із сіллю»: у наївній схемі `sha256(сіль‖файл)` можна
дописати дані в кінець файла й перерахувати правильний підпис, не знаючи
солі. HMAC це виключає.

Ключ лежить **тільки на станції**, у `/etc/vrx-update.key`, режим 600.
На флешці його бути не повинно.

## Як зібрати оновлення

1. Створити каталог `VRX-update` на флешці.
2. Скласти в нього змінені файли, дотримуючись структури станції.
3. Запустити генератор (потрібна копія ключа на машині розробки):

```bash
./make_update.sh /media/usb/VRX-update ./vrx-update.key 20260815
```

Він обійде всі файли, порахує підписи й запише `update_list` та
`version.txt`. Файли `version.txt` і `update_list` у список не
потрапляють.

Вручну підпис одного файла рахується так:

```bash
KEY=$(cat vrx-update.key)
openssl dgst -sha256 -hmac "$KEY" -r VRX-update/build/vrx_gl
```

## Що станція робить із файлами

- **Спершу перевіряє все, потім копіює.** Якщо хоч один файл відсутній
  або не пройшов підпис — оновлення скасовується повністю, станція
  піднімається на старій версії.Напів-оновленого стану не буває.
- **Права відновлюються.** FAT не зберігає біт виконання, тому для
  наявного файла береться режим старого, а для нового — 755, якщо він у
  `build/`, `scripts/` або має розширення `.sh`, інакше 644. Без цього
  `build/vrx_gl` приїхав би невиконуваним.
- **Заміна атомарна** — через тимчасовий каталог і `mv` у межах однієї
  файлової системи.
- **Нічого не видаляється.** Файли, яких немає в списку, лишаються як є.
  Прибрати файл зі станції оновленням неможливо.
- Каталоги, яких бракує, створюються самі.

## Куди дивитись, якщо не спрацювало

```bash
journalctl -b -u vrx-update
```

Типові причини:

| у логу | що це |
|---|---|
| `[ПІДПИС!]` | файл не збігається з підписом — пересобери список |
| `[нема]` | файл є в списку, але його немає на флешці |
| `недопустимий шлях` | абсолютний шлях або `..` у списку |
| `немає ключа` | на станції немає `/etc/vrx-update.key` |
| нічого немає | версії збіглись, або каталог `VRX-update` не знайдено |
